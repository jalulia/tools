Three places to check

PlaceWhat it can showWhat it does not prove
Visible transcriptText already streamed to the screen.That the text reached the working window or persistent record.
Working contextMaterial sent to the next model call.That the entire visible transcript is included.
HELIX and filesSuccessfully stored strands and artifacts.That a failed turn was stored, or that all local data has synced.

A turn fails or stops

  1. Preserve what you can see.

    Copy needed text and save available files before refreshing, retrying or restarting.

  2. Read the actual error.

    Identify whether it came from the provider, connection, tool or app. A later error does not explain an earlier failure by itself.

  3. Check for completed side effects.

    An output or file edit may already exist even if the turn failed. Inspect it before repeating a request that writes or deletes.

  4. Restate the missing request.

    Include any needed text from the failed turn. Ask Mir to verify existing outputs and retrieve the relevant strands before continuing.

V05 described an incident where streamed questions could not be recovered from the record. That is a useful failure example, not proof that every failure has the same persistence behaviour.

Provider errors

Read the error message before choosing a remedy. Credit and rate-limit failures are possibilities; network errors, authentication, unavailable models, invalid requests and service failures are others. A retry may need time, a corrected configuration or another available model.

A provider failure does not establish that no record or artifact was written earlier in the turn. Verify what exists before resending.

A model switch appears stalled

Wait for the active turn to settle or use Stop before changing models. The frontend says changes apply from the next message. If a switch appears stalled, preserve visible work, inspect the status, then send a new message that states what should continue and which files already exist.

The shared record is the intended continuity path. This review did not run a model-switch experiment or verify that every vendor resumes a mid-tool turn equivalently.

Other cases

SymptomUseful next check
Loading does not finishPreserve work. Inspect connectivity and app status; record loading can contribute, but a large HELIX is not the only possible cause.
Mir cannot see an earlier imageAsk for the original file to be read again. In the public source, earlier image payloads are scrubbed from context to reduce its size.
A recalled passage is irrelevantAsk Mir to identify its source and verify the intended context instead of adopting it as an instruction.
Task state or files differ between devicesCheck the local result and account archive separately. A visible local update is not proof of completed sync.
A browser tool fails to launchUse an available text fetch or another supported tool, and state what could not be checked visually.
Work seems missing after an updateCheck saved outputs, drafts and the account archive. Avoid assuming that a reinstall or restart will restore unsynced work.
