Upload, mount and scan

OperationEstablished by the operationSeparate check
UploadA file is accepted into the session’s Input list.Whether Mir has read it, extracted the right content or used it in the reply.
Mount folderThe supported local access path is associated with a folder.Which tools are available, how access is enforced, and whether a particular file was opened.
ScanThe frontend requests conversion and reports status; a resulting HELIX can appear under Output.Whether conversion completed correctly and whether the record was mounted or included in recall.

Scanner’s + accepts one or more files. Its folder button appears when a mount is active. Status is transient: the installed loadScanList() is empty, so the panel is not a persistent scan history. The source scanner handles text-bearing formats; image-only files may require extraction or OCR elsewhere.

The × controls

LocationFrontend actionBoundary
Output / Drafts / InputAsks “Delete [filename]?” and sends a DELETE request after confirmation.The readable frontend does not establish archive retention or recovery. Save a needed copy first.
FolderClears local UI references, the desktop mount-active flag and the folder display.The function does not itself call a backend unmount route. Full native or server handle revocation is unverified.
To DoRequests deletion of the selected goal or task.This changes the plan’s state; it does not establish what happened to associated files.

Do not treat ending a session as a verified guarantee that every folder handle has been revoked. That was an unsupported assurance in V05.

Drafts and outputs

The source’s document workflow opens a draft, appends content and finalizes it. Drafts persist in files as work progresses; finalization can convert Markdown into PDF or DOCX. Files created through other tool paths need not use that workflow.

A saved draft can preserve earlier chunks when generation is interrupted, but it is not immune to disk, sync or deletion failures. Check what is actually present before resuming. Finalization is a file-state transition, not a quality review.

Tasks

The To Do panel renders goals and steps, with checkboxes and deletion controls. The installed frontend sends changes to the session’s task routes. A checked box means marked done. It does not certify that a file exists, that dependencies were satisfied in practice or that a reviewer checked the result.

Tool families and their boundaries

FamilyPurposeEvidence boundary
MemoryRead earlier strands and retrieve stored material.Positional reads are in public source; newer reach and provenance behaviour were reported by V05.
Session filesRead inputs, write drafts, finalize outputs and access archives.Public-source workflows plus installed file-panel routes.
WorkspaceRun code and maintain files in a server workspace.Public source; current persistent-terminal behaviour is not independently reproduced.
Local filesOperate on files through the mounted-folder bridge.Installed frontend and bridge paths. Desktop and browser implementations differ.
WebFetch, search or use an available browser tool.Tool availability depends on the running backend and environment.
ImagesGenerate or edit images through an available image tool.Do not infer visual accuracy from successful generation; inspect the resulting pixels.
WorkersDelegate a separate job to a background process.Worker schemas and completion handling described in V05 have not been revalidated against this compiled backend.

The public source sets a 15-round tool loop and a 300-second wall-clock guard, checked between rounds. If either guard is reached, its final synthesis call has a 45-second timeout. Provider requests, image generation, desktop bridges and worker tasks can have different waits. These values are not an end-to-end response-time promise.

Background workers

V05 reported up to nine workers, separate workspaces, selectable models and a scanned completion report. Those are inherited runtime observations, not limits confirmed by this review. Ask the active runtime for its tool schema and inspect the produced report before relying on a particular limit or workflow.

Automator is distinct: it sends continuation messages into the main conversation. A background worker runs a separate job.
