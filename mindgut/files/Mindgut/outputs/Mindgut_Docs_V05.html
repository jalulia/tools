Chapter / 01

What Mindgut does

Mindgut is a workspace for ongoing work with Mir, its AI assistant. Read and create files, manage tasks, and switch models within the same conversation. Mindgut stores completed exchanges in HELIX, a persistent record used to bring earlier material into later replies.

01The workspace02The record03How they fit together04What Mindgut is not

The workspace

You talk to Mir in a chat column. A sidebar holds the session's controls and readouts. Mir can read files you add, write files you can download, keep a task list, run code in a workspace, search the web, and dispatch background workers for longer jobs.

The model behind Mir is yours to choose. Fourteen models from four vendors are on the roster, and you can switch between them at any point without starting over. An effort level, from low to max, sets how much work the chosen model puts into each reply.

The record

When an exchange completes, Mindgut writes it to the HELIX: a single file that belongs to your account and grows with every conversation. Each entry is called a strand. The file holds what was said, who said it, and a set of measurements taken from the text itself.

Later turns draw on the record in two ways. Before every reply, Mindgut selects a small set of earlier strands and places them in front of the model automatically. Mir can also search the record on purpose, by concept or by exact phrase, and quote from it. Chapter 05 explains both.

How they fit together

The model's own context is deliberately short: at most seven exchanges, trimmed to four when it fills. The HELIX is the long memory. This is why switching models mid-conversation works: the record and the recall step are the same regardless of which model is reading them.

What Mindgut is not

NotBecause
A long-context chatThe context holds seven exchanges at most. Earlier material returns through the record, not by scrolling back.
A summariserNothing in the record is model-written prose about the conversation. Strands hold the exchange itself and numbers measured from it.
A vector databaseRecall works on letter-class measurements and word co-occurrence. There is no embedding model.
A fine-tuned modelNo weights change. What changes is the record, and therefore what the next turn is given.

Chapter / 02

Getting started

Open the app, sign in, pick a model, and type. Everything else can wait until you need it.

01First session02Model and effort03Adding files04Where outputs go05Normal and advanced06For developers

First session

  1. Open the app. A local server starts and the window opens on it. A loading screen runs until your HELIX is ready.
  2. Sign in. Your account's HELIX opens and a session starts on it. A new account begins from a founding record of 187 strands, so every record shares the same origin.
  3. Type a message and press Enter. While Mir is working you can keep typing; a message sent mid-turn is queued and delivered at the next pause in her work.
  4. Pick up where you left off. A new session on the same account continues the same record. Restored messages from the previous session appear above a "previous session" divider. Expect the first few turns to be a warm-up as recall settles.

Model and effort

Two selects at the top of the sidebar choose the model (grouped by vendor: Claude, ChatGPT, Gemini, Grok) and the effort level (low, medium, high, xhigh, max). A change applies from your next message. The session, its history and the HELIX continue unchanged. The choice is stored on the device, not with the account.

Higher effort means more work per reply and more usage. The default is the current Claude model at xhigh.

Adding files

Three different operations put files in reach of Mir. They are easy to confuse, and they do different things.

OperationHowWhat it does
UploadDrop a file on the chat, or use +Places the file in the session's Input list so Mir can read it.
Mount a folderFolder row in the sidebarGives Mir read and write access to a local folder for the session. Mounting does not upload or scan its contents.
ScanScanner row in the sidebarConverts a file into HELIX form so Mir can mount it as a second record and search it by the same geometry as memory. Scanning is separate from uploading.

Chapter 06 covers each in detail, including what the × controls do in each row.

Where outputs go

Files Mir creates appear in the sidebar under Output. Documents still being written appear under Drafts. Your uploads appear under Input. Click a file to download it. Outputs persist in your account archive across sessions.

Normal and advanced

The gauge icon in the top bar switches between normal and advanced mode. Normal shows files, folder and tasks. Advanced adds the instrument panels, Tokens, Hₜ, Respiration, Ø and HELIX, and per-message timestamps and status marks. The setting is remembered on the device. Chapter 04 explains each panel.

For developers

The public source runs as a web server or a desktop app. The scanner also runs on its own from the command line, turning any file into a HELIX without a model.

git clone https://github.com/The-Impossible-Outcomes-Co/mindgut
pip install -e ".[desktop]"
export ANTHROPIC_API_KEY=…
python -m mindgut.server                      # web, :8080
MINDGUT_DESKTOP=1 python -m mindgut.desktop   # native window
python -m mindgut.engine.scanner in.pdf out_HELIX.json

The public source lags the shipped build. Which parts of this document are verified against source and which against the installed app is recorded in the reference.

Chapter / 03

What the model receives

On every turn the model sees three things: a short window of recent exchanges, a small set of strands recalled from the record, and your message. It does not see the whole conversation.

01The window02Automatic recall03Deliberate recall04What "I remember" means

The window

The window is the list of recent exchanges sent to the model. An exchange is one message from you plus everything Mir did in reply, tool calls included, ending in her final text.

The window grows one exchange at a time until it holds seven. Then the oldest three are released and it continues from four. Released exchanges are not lost; they are already in the HELIX and can return through recall. This is the 7 → 4 cycle shown by the Respiration panel.

Separately, the sidebar reports a session renewal every 21 exchanges. What renewal changes is not documented in the public source; the count is visible, the effect is not. It is not the same thing as the 7 → 4 release.

Automatic recall

Before each reply, Mindgut selects a handful of strands from the record and places them in front of the model. You do not see this selection and Mir cannot decline it. The selection is made by measurement, not by topic: strands are chosen for where they sit relative to your message in the phase space described in Chapter 05. They can look off-topic. Treat them as peripheral vision: enough for Mir to notice that a subject has a history, not a substitute for looking it up.

Messages can also arrive with bridges: short blocks marked [strand N] from your record or [doc_strand N] from the bundled Paradox Field Dynamics book, attached when two words in your message close a line in one of those records. Bridges are matched on words, so a bridge can be irrelevant to what you meant.

Deliberate recall

Mir can also read the record on purpose. She can reach by concept, read a range of strands by position, or search for an exact phrase. Each search reports how many strands carry a concept on your side and how many on hers, so she can tell the difference between something you said and something she wrote.

A match means the phrase occurs in the record. It does not mean the person who wrote it endorsed it; people quote, reject and paste other people's words. No match means the search did not find one in the available record by this method, not that the thing was never said.

Results from these searches are trimmed out of the window after the turn, so the context does not re-absorb what the record already holds.

What "I remember" means

When Mir says she remembers something, it can mean one of three things, with different reliability:

  • It was in the window. The last four to seven exchanges. Reliable.
  • She looked it up. A deliberate search returned it, with a strand number. Reliable, and checkable.
  • It surfaced automatically. The recall step placed it in front of her. Real, but selected by geometry; the connection to your message may be loose.

Ask which. A strand number is the receipt.

Chapter / 04

The sidebar

Eleven panels. Five are readouts that describe the session; the rest change it. Select a panel to read what it shows and what you can do with it.

01Panel by panel02Readouts03Controls04The top bar

Panel by panel

Readouts

Tokens, Hₜ, Respiration, Ø and HELIX describe the session. Interacting with them changes nothing. They are shown in advanced mode only.

Tokens

Cumulative usage for the session: the number of model calls, and input, output, cache and thinking tokens. One exchange can make several calls. The fields overlap in ways that differ by provider, so they should not be added together, and they are not a bill. They are not the size of the current window or of the HELIX.

Hₜ

A heat value computed after each exchange, shown on a 0–60 bar with three lights for the accompanying status level. Green is the usual state.

Respiration

Four cells, for four to seven exchanges in the window. At seven, the oldest three are released and the window returns to four; the vent light marks that release. The separate number is the total exchange count for the session. The line beneath counts renewals, which happen every 21 exchanges and are a different event from the release.

Ø

The number of active tension tags held by the memory system: markers minted when an exchange left something structurally unresolved. The count is shown; the tags themselves are not visible in the interface. "Ø 11" means eleven held tags, not eleven errors, tasks or questions.

HELIX

The total number of strands in your record, with a bar showing how much is founding material (cyan, inherited by every account) and how much is organic (purple, added by yours). A strand is one record unit, not one exchange; an ordinary exchange writes more than one. The wave icon opens the timeline view; the circular icon opens the 3-D view. The count is the quickest check that an exchange was written.

Controls

Model and effort select the next model call. Folder changes what Mir can read and write. To Do changes task state. Automator can send messages on your behalf.

Account, model and effort

Described in Chapter 02. Changes apply from the next message.

Folder

Shows the mounted folder, or "No folder". Click to mount; Mir then has the local file tools over that folder for the session. The × clears the mount from the interface. Whether it also revokes every server-side handle to the folder is not verified; if that matters, end the session.

Scanner

The + scans one or more files into HELIX form. When a folder is mounted, a second button scans the whole folder. The panel shows a brief status while the scan runs and then clears; the resulting file appears under Output. There is no persistent list of scans in this panel. A completed scan does not by itself add the file to automatic recall; Mir mounts a scanned HELIX on request.

To Do

Mir's task tree. Checking a box marks a task done; the delete control removes it. "Done" records that the task was marked complete. It does not mean an output exists or was reviewed.

Automator

Desktop only. Sets a maximum number of automatic replies (1–25; default 7). Once armed, Automator watches for Mir's reply to end with an exact trigger phrase and, when it does, answers for you so that Mir continues. Each automatic reply is an ordinary turn and uses the model normally. If you type while it is armed, your message takes precedence and the loop pauses. Stop disarms it; so does the count running out, a failed turn, a reply that ends another way, or a new session.

Automator is not the worker-agent system. It advances one exchange at a time in the main conversation. Workers run separate tasks in separate workspaces and report back.

Output, Drafts, Input

The session's file lists. Click a file to download it. The × asks for confirmation and then requests deletion from the server. Whether the archive copy survives that request is not verified; download first if in doubt.

Chapter / 05

Memory

The HELIX is written by code, not by a model. This chapter explains what goes into it, how each exchange is measured, and how those measurements drive recall.

01The file02How text is measured03What a strand holds04How recall selects05Tension tags06The viewers

The file

The HELIX is one JSON file per account. It is append-only in normal use: after each completed exchange, Mindgut adds an exchange strand holding the text and a summary strand holding measurements. Nothing is rewritten.

Every account starts from the same 187 founding strands, so every record shares an origin. The file is loaded whole each time it is read, and grows by roughly 8 KB per exchange. On desktop it lives in the app directory and is synced to the account after each exchange.

How text is measured

Each letter A–Z is numbered 1–26 and reduced to a single digit by adding its digits until one remains (so 14 → 5, 26 → 8). The result places the letter in one of three classes:

  • A — roots 1, 4, 7
  • R — roots 2, 5, 8
  • D — roots 3, 6, 9

Digits, punctuation and non-Latin characters are ignored. For any passage, the share of letters in each class is its phase: three fractions that add to one. Balance is the A share minus the D share. σB is how much balance varies from clause to clause across a sliding window of seven clauses; a single clause has no σB.

The classes are near-even across English as a whole: in a 370,105-word list, 33.4 / 33.3 / 33.3 percent. Individual passages depart from that.

Mindgut measures your text and Mir's separately on every exchange. The distance between the two phases is called clash.

What a strand holds

Strand typeWhat it holds
foundingThe 187 strands every account begins with.
exchangeYour text, Mir's reply, both phases, and the list of tools she used.
summaryNumbers only: balance drift, dominant class, per-sentence measurements. No prose.
ghostA strand whose text has been released. The header and position are kept.
file_eventWritten when a file is uploaded, finalized or drafted.

How recall selects

Automatic recall places seven strands in front of the model each turn: the origin strand, three chosen for being nearest the line from your message's phase toward each class corner, and three chosen for being furthest from your message's phase, one per class. A second pass adds sentence-level joints whose class transition and clash resemble your message. The selection is deterministic and makes no model call.

Deliberate recall, described in Chapter 03, works differently: Mir names a concept or a phrase and the record is searched for it. Concept search returns, first, a count of strands carrying each concept on your side and on Mir's, and then the best crossings with their strand numbers.

Tension tags

After each exchange a small ternary check decides whether the exchange resolved or left something open. When the A–R–D cycle stalls, a tag is minted from three words in the text and held. Held tags are included in automatic recall, and their count is the Ø readout in the sidebar. Tags are word triples, not statements of meaning, and the interface does not currently show them.

The viewers

From the HELIX panel, the wave icon opens the record as a timeline and the circular icon opens a 3-D view with a legend of strand types. Both open in the system browser. They are for looking, not editing.

Files, tasks and tools

How files reach Mir, how she writes them back, what the task board does, and what she can call.

01Upload, mount, scan02The × controls03How Mir writes files04Tasks05What Mir can call06Background workers

Upload, mount, scan

OperationEstablishesDoes not establish
UploadThe file is in the session's Input list. Mir can read it: PDF pages, text lines, images as vision, Office documents, zip.That it was scanned, or that it is part of recall.
Mount folderMir has read and write access to the folder for this session, on desktop through the app and in a browser through the file-access API.That any file in it was uploaded or scanned. Mounting touches nothing until Mir is asked to.
ScanA HELIX-form copy of the file exists under Output. Mir can mount it as a second record and search it by geometry.That it joined automatic recall. Mounting a scanned HELIX is a deliberate step.

Re-scanning an unchanged file produces a second copy with a numbered suffix.

The × controls

The same glyph does different things in different rows.

  • Output, Drafts, Input × — asks for confirmation, then requests deletion from the server. Whether an archive copy survives is not verified. Download first if the file matters.
  • Folder × — clears the mount from the interface. Whether every server-side handle is released is not verified. Ending the session is the sure way.

How Mir writes files

Mir writes files in small pieces: open, then append in chunks, then finalize. A document being written appears under Drafts; finalizing moves it to Output and, for .docx and .pdf, converts it from markdown. A draft that is interrupted keeps everything written so far and can be resumed.

This is deliberate. A file emitted in one piece can be lost silently if the model's output is cut off mid-way. A draft on disk cannot.

Tasks

Mir keeps a task tree: goals with ordered steps, dependencies between steps, and a status for each. She updates it through a tool; you see it in the To Do panel and can check items off or delete them there. A goal resolves when all its steps are done. The board is a plan, not a record of outputs: "done" means marked complete.

A turn allows up to fifteen tool rounds before Mir is asked to wrap up, with 45 seconds per round. Results from memory tools are trimmed from the window after the turn. Large results from other tools are shortened once they are two rounds old.

Background workers

For long jobs Mir can start up to nine workers that run while the conversation continues. Each works in its own directory, with any model on the roster and its own effort level. When a worker finishes, its report is scanned into a HELIX under Output, and Mir reads it strand by strand. Nothing a worker writes enters your record directly.

Chapter / 07

When something fails

Three places hold the conversation, and they do not fail together. Knowing which one you are looking at tells you what to do next.

01Three places02A failed turn03Provider errors04A stalled model switch05Other known cases

Three places

PlaceWhat it isWhen it is written
The visible transcriptWhat is on your screen.As text streams, including text from a turn that then fails.
The windowThe exchanges sent to the model.When an exchange completes. A failed turn may not be in it.
The HELIXThe permanent record.When an exchange completes. A failed turn is not in it.

Text you can see is not necessarily text Mir can see, and it is not necessarily text the record holds.

A failed turn

If a turn fails after text has appeared, copy anything you need before retrying. Then restate your request directly in the next message. Do not assume Mir can recover the failed turn from memory; it may not have been written.

The case that established this: a turn failed on a connection error after Mir's reply, containing five questions, was already on screen. The questions were not recoverable from the record. In the next turn Mir answered an earlier list until the five were restated. The visible transcript, the window and the HELIX had diverged. This is a known recovery boundary; the underlying cause of that particular failure is not established.

Provider errors

When a model vendor refuses a call, the usual reasons are an exhausted credit balance or a rate limit. The error is shown in the chat and the turn ends. Nothing is written to the record for that turn. Switch to a model from another vendor, or wait, and send the message again.

A stalled model switch

Switching models while a turn is mid-way through tool calls can stall that turn. Send the next message; the new model picks up from the record. If text from the stalled turn was on screen, treat it as described above. A credit error on the new model identifies one failed call; it does not explain a stall that happened before it.

Other known cases

  • Blank replies with no error. Seen when a vendor key is missing or expired. Check the model select; try another vendor.
  • A loading screen that does not finish. The app waits for the HELIX to load. A large record takes longer. Give it time before restarting.
  • An image Mir can no longer see. Images are removed from the window after a turn to save space. Mir can re-read a file by calling for it again; ask her to.
  • An irrelevant bridge. A [strand N] block attached to a message by word match rather than meaning. Ignore it, or tell Mir to.
  • Task board out of sync. If syncing fails, the board stays local and continues to work; it catches up later.
  • A headless browser that will not start. Some machines block it. Mir can fetch pages as text instead.
  • Lost work after an update. The desktop app replaces its bundle after it quits. Session files are kept in the app directory; if something seems missing after an update, check Output and the account archive before assuming it is gone.

The version boundary

The public repository ends on 1 August 2026. The installed build is dated 20 October and ships compiled Python. For anything added in between, the readable evidence is the frontend, the log and the data files. Specifically, these are observed in 2.2.58 and absent from source: geometric reach and its provenance header, margin bridges, read_field, worker agents, terminals, the model and effort selects and their routes, sync, the self-updater, and non-Anthropic model routing.

Version-bounded statements

  • Hₜ. In the public source, heat is computed after each exchange and the output limit is max(4096, base) regardless of its value (controllers.py:341). The 2.2.58 frontend displays H_t and directives.heat_level. Whether the 2.2.58 backend uses heat elsewhere is unverified. The chapters therefore describe Hₜ as a readout and do not say it has no effect.
  • Renewal. The sidebar reports "renewed ×n · next at 21" (42 before 2.2.46). No public source describes what renewal does.
  • Model switch continuity. Reported in release notes and by users. The switch control exists; no switch was performed in the measured session. Not reproduced.

Open questions

Six behaviours the installed build shows but the readable evidence does not explain. Each needs an answer from the backend. Until then the chapters describe what is visible and stop there.

01For the backend02Other gaps

For the backend

  1. Renewal. What state changes at the 21-exchange renewal in 2.2.58? The sidebar counts it; nothing readable describes its effect.
  2. Heat. Does any 2.2.58 backend path consume H_t or directives.heat_level beyond sending them to the frontend? In the public source the answer is no.
  3. Scanner and recall. After a scan completes from the sidebar, is the resulting HELIX mounted, merged, indexed, or enrolled in automatic recall without a further step?
  4. File and folder lifecycle. What does the file-panel DELETE remove: the session reference, or the archive copy as well? Does the folder × release every server-side and native handle?
  5. Token accounting. What resets the session totals, and how are cache and thinking fields normalised across the four vendors?
  6. Tension tags. What resolves a tag, where is resolution recorded, and is there an intended way for a user to see the held tags?

Other gaps

  • The public source lags the build by eleven weeks. Reach, bridges, read_field, agents, terminals, model and effort routes, sync and the updater are unreadable.
  • Non-Anthropic routing is not in source. How 2.2.58 reaches ChatGPT, Gemini and Grok models is not documented.
  • Bridges attach by word match. There is no visible score or reason, and no threshold or toggle.
  • The HELIX is one file loaded whole. At roughly 8 KB per exchange this is the limit most likely to be felt first.
  • Model and effort are stored per device, not with the account.
  • Cross-model continuity is reported, not demonstrated.
  • Diagnostics already exist in the markup, hidden: gate result, per-class phase bars, drift, lattice surface. They are one CSS rule from being visible in advanced mode.

Glossary

Terms as this document uses them. Where the runtime's own name differs, both are given.

Terms

A · R · D
The three letter classes, by digital root. The runtime also writes them 147, 258, 369 and calls them cosets.
Aside
A message typed while Mir is working; delivered at the next pause in her tool use.
Automator
Desktop-only panel that sends up to a set number of automatic replies when Mir's reply ends with an exact trigger phrase.
Balance
The A share minus the D share of a passage.
Bridge
A [strand N] or [doc_strand N] block attached to a message because two of its words close a line in that record. Matched on words.
Carbon · Silicon
Your text and Mir's text, measured separately. Searches report how many strands carry a concept on each side (a, b).
Clash
The distance between the carbon and silicon phases of one exchange.
Effort
One of five levels (low, medium, high, xhigh, max) setting how much work the active model puts into a reply.
Exchange
One message from you plus everything Mir did in reply, tool calls included.
Founding
The 187 strands every account's record begins with. Shown in cyan on the HELIX bar.
HELIX
The JSON file holding a record and its strands. Your account's memory HELIX is the record; a scanned file gets its own.
Hₜ
A heat value computed after each exchange and shown in the sidebar.
Joint
A sentence-level match between your message and a strand, added to automatic recall.
Mir
The assistant you talk to; the name the runtime gives whichever model is active.
Organic
Strands added by your account, as distinct from founding. Shown in purple on the HELIX bar.
Phase
The three shares (A, R, D) of a passage's letters; a point in a triangle.
Reach
Deliberate recall by concept, returning a provenance header and the best crossings with strand numbers.
Record
Your account's HELIX.
Renewal
A session event every 21 exchanges, counted in the Respiration panel. Effect undocumented.
Respiration
The 7 → 4 cycle of the window: grow to seven exchanges, release the oldest three.
Scanner
The converter that turns any text-bearing file into a HELIX. Letters only; no model.
σB
How much balance varies from clause to clause across a sliding window of seven clauses.
Strand
One record unit in a HELIX. Types: founding, exchange, summary, ghost, file_event.
Summary strand
The numbers-only strand written after each exchange: balance drift, dominant class, per-sentence measures.
Tension tag (Ø)
A word triple minted when an exchange left something structurally unresolved; held and counted as Ø in the sidebar.
Window
What the model is sent on a turn: the recalled strands, then the last four to seven exchanges, then your message.
Worker
A background agent Mir can start for a long task; up to nine at once, each in its own directory.
