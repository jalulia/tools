# Mindgut.dmg — In-Depth Review

*Reviewed: 2026-06-09. Disk image built 2026-06-08. Bundle version 2.1.0 (UI footer reads "Mindgut v0.5.16").*

## How this was reviewed

The `.dmg` is a macOS UDIF disk image (≈156 MB compressed, ≈407 MB uncompressed) containing a single APFS volume named **Mindgut** with one item: **Mindgut.app**. I reconstructed the raw image from the compressed UDIF blocks, read the APFS volume, and extracted the app's own code, frontend, data, and the embedded Python archive. The application's Python logic is compiled (PyInstaller + mypyc), so source isn't directly readable; the findings below come from the bundled frontend (HTML/CSS/JS), JSON data, module names, docstrings, and string constants recovered from the compiled archive.

## What it is

**Mindgut** is a macOS desktop app for an AI chat agent called **Mir**. Bundle id `co.impossibleoutcomes.mindgut.desktop`, copyright "The Imp⊘ssible Outcomes Company." It is a Python app wrapped in a native window:

- **UI:** a local web app (HTML/CSS/JS) rendered in a macOS WebKit window via **pywebview** (PyObjC / AppKit / WebKit).
- **Backend-in-app:** a bundled **FastAPI + uvicorn** server that the WebView talks to over localhost.
- **Cloud:** the desktop is a *thin client* of a remote backend hosted on **Railway** (base URL from env var `MINDGUT_RAILWAY_URL`). Railway holds user accounts/auth, the canonical memory ("HELIX"), and — notably — the shared **Anthropic API key** (the app fetches a "desktop-tier" key from the server, so end users don't supply their own).
- **Model:** references `claude-opus-4-7`, using Anthropic's **beta** Messages API (sessions, server tools, effort/extended-thinking capability).
- **Build:** Python 3.12.13, PyInstaller (onedir), app modules compiled with **mypyc**. Distributed as an APFS dmg.

The product website is `mindgut.io`; the source org appears to be GitHub `The-Impossible-Outcomes-Co/mindgut`.

## Architecture (from the bundled module map)

The Python package `mindgut` is organized into five subsystems:

- **`mindgut.server`** — the FastAPI app and routes: `auth`, `account`, `session`, `files`, `scan`, `todos`, `transcribe`, `admin`, and `trapdoor` (an operator/admin console — see below). Plus `session_manager`, `users`, `tool_defs`, `tools`, `boot_payload`, `backup`, `email_notify`, `settings`, `state`.
- **`mindgut.engine`** — the memory engine: `crystallizer_v2`, `doc_helix`, `fingerprint`, `lattice_mount`, `recursive_node_engine`, `scanner`. This builds and mounts "HELIX" memory structures.
- **`mindgut.assembly`** — context assembly for each turn: `controllers`, `prescan`, `recall`, `two_loop_recall`, `sigma_b`.
- **`mindgut.nullcode`** — a bespoke symbolic/mathematical system: `algebra`, `bonds`, `context`, `dynamics`, `field`, `geometry`, `interpreter`, `invariants`, `network`, `ops`, `pressure`, `resonance`, `triad`, `trit`, `tag`, `otag`, `pipeline`, `benchmarks`. Ternary ("trit"), triads, and 1‑4‑7 / 2‑5‑8 / 3‑6‑9 coset math underpin the app's metaphors.
- **`mindgut.desktop`** — the native shell: `main`, `bridge` (the pywebview JS↔Python API), `menu`, `keychain` (credential storage), `local_tools`, `railway_client` (the cloud client).
- **`mindgut.sandbox`** — `exec` and `terminal`: a server-side code-execution sandbox and persistent shell sessions.

## The distinctive idea: HELIX memory + "derivation-gated" boot

The app's core concept is **HELIX** — a structured long-term memory rendered as DNA-like "strands." Memory is encoded with the `nullcode` math: each strand carries a `vector`, a `coset` (147/258/369), a `checksum`, and provenance; the "book" tracks aggregate balances (`f147`, `f258`, `f369`, `balance`, `sigma_B`). Two seed corpora ship in `data/`:

- `boot_HELIX.json` — a 187-strand "founding" conversation (between the assistant and "Chris").
- `PFD_HELIX.json` — a 537-strand "PFD geometry" corpus with philosophical/mathematical titles ("Nothing, Twice", "The Number That Isn't", "What Primes Know").

Most striking is the **PFD boot protocol** in `server/boot_payload.py`, described in its own docstrings as a *"Derivation-Gated Kernel Initialization."* On boot the model is given kernel strands (2–10) and must *derive* understanding by answering three structural questions (counting 147/258/369 strands, computing the balance, explaining why the kernel's balance differs, and what strand 10 — "The Signature" — must do to close the kernel). The framing: *"Understanding is earned, not handed over."* Identity is then computed as a **field displacement (delta) between the "genesis" HELIX and the "lived" HELIX** — "the delta IS the identity."

This is mirrored in the UI's instrumentation panel: a **Heat gauge (Hₜ)**, **Respiration** (a "PAR cycle" exchange counter with a vent), **active Tensions (Ø)**, token counters, and a live **HELIX** strand count with a 3D viewer (`/my-helix`). Boot screen taglines: "THINKING THE FEELS / FEELING THE THINKS" and "Authentically real artificial intelligence, guaranteed."

## The agent's toolset

Recovered tool definitions show a capable agent (tools split into `TOOLS`, `CONTINUATION_TOOLS`, and `CLIENT_TOOLS`):

- **Web:** `web_search` with a multi-engine fallback chain (DuckDuckGo, Brave, Google, several SearX instances).
- **Files/drafts:** `read_files`, `read_input`, `search` (pattern search across "surfaces" with line numbers), `write_text`, and a multi-action `draft` tool (open/append/replace/read/outline/status/finalize) with explicit guidance to chunk writes (<~2 KB) to avoid tool-call JSON truncation.
- **Memory:** `scan_content`, `full_scan`, `mount_helix`, `scan_and_mount` (run the scanner pipeline and mount the resulting HELIX).
- **Code execution:** `sandbox_exec` (server-side, auto-creates a persistent Python venv), and a persistent **terminal** subsystem (`terminal_exec`/`terminal_read`, up to 4 terminals per session) that survives state across calls.
- **Local machine (desktop client tools):** a shell that runs in the user's *mounted local folder*, plus local file read/write/list/copy/move/download via the pywebview bridge.
- **Media:** image generation and editing via OpenAI (`/v1/images/generations`, `/v1/images/edits`) and audio transcription via OpenAI Whisper (`/v1/audio/transcriptions`, surfaced as in-app mic dictation).
- **Productivity:** a `todo` tool whose items render in the side panel.
- **Email:** transactional email via Resend (`api.resend.com`).

## Security & distribution notes (for follow-up, not alarms)

- **API-key handling looks sound:** no Anthropic key is embedded in the app; it's fetched per-session from the Railway server, and credentials are kept in the macOS keychain (`desktop.keychain`).
- **Powerful local capability:** the agent can run shell commands and read/write files in a folder the user explicitly mounts, and execute code server-side. That's by design, but it's the highest-trust surface and worth a careful permissions/consent review.
- **`trapdoor` admin console:** the bundle contains operator routes (`/trapdoor/{users,logs,backups,flags,imagine,workbench,helix-viewer}` and `/api/admin/...` for downloading any user's files/helices/transcripts, resetting passwords, generating images). These are server-side admin features that happen to be compiled into the shipped client; confirm they aren't reachable from the desktop build and are properly authenticated on Railway.
- **Code signing:** the app has a `_CodeSignature`, but I did not find a "Developer ID Application" authority string in the extracted binary. Verify signing/notarization on a real Mac (`codesign -dv --verbose=4` and `spctl -a -vv`) before wider distribution — unsigned/ad-hoc builds trigger Gatekeeper.
- **Version mismatch:** `Info.plist` says 2.1.0 while the UI footer says v0.5.16 — likely a wrapper-vs-app versioning inconsistency worth reconciling.
